Resiliência

Estratégia planejada para a Fase 3 — a ser implementada após a Fase 2 (Observabilidade + Cache).

Status atual: ⏳ não implementado — o sistema não possui tolerância a falhas além do timeout de 30s no WebClient.

O problema atual

O SpeechToTextClient faz uma chamada bloqueante ao Whisper com .block(Duration.ofSeconds(30)). Se o Speaches estiver lento, sobrecarregado ou offline: 

  Requisição do cliente
         │
         ▼
  SpeechToTextClient.transcribe()
         │
         │  .block(30s)  ←── thread bloqueada por até 30 segundos
         ▼
  Speaches (pode estar lento / offline)
         │
         │  timeout ou erro
         ▼
  TranscriptionException("Falha na comunicação com Whisper")
         │
         ▼
  HTTP 400  ←── sem retry, sem fallback, sem circuit breaker

Sob carga, threads acumulam esperando o timeout → pool de threads esgotado → cascata de falhas.

Solução planejada — Resilience4j

Padrões aplicados em camadas sobre o SpeechToTextClient, na ordem de execução: 

  Requisição
       │
       ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  Retry  (v3.2.0)                                            │
  │  maxAttempts=3 · backoff 500ms → 1s → 2s (exponencial)      │
  │  retry apenas em TranscriptionException (I/O)               │
  │  não faz retry em IllegalArgumentException (validação)      │
  └───────────────────────────┬─────────────────────────────────┘
                              │ (se ainda falhar após 3 tentativas)
                              ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  Circuit Breaker  (v3.1.0)                        estado:   │
  │                                                             │
  │  CLOSED ──(≥50% falhas em 10 calls)──► OPEN                 │
  │    ↑                                      │                 │
  │    └──(3 calls ok em HALF_OPEN)──◄── (30s espera)           │
  │                                      HALF_OPEN              │
  └───────────────────────────┬─────────────────────────────────┘
                              │ (se OPEN → vai direto pro fallback)
                              ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  Fallback                                                   │
  │  TranscriptionException("Whisper indisponível")             │
  │  → GlobalExceptionHandler → HTTP 503 ProblemDetail          │
  └─────────────────────────────────────────────────────────────┘

Estados do Circuit Breaker

EstadoComportamentoTransição
CLOSED Operação normal — todas as chamadas passam para o Speaches → OPEN se ≥ 50% das últimas 10 chamadas falharem
OPEN Circuito aberto — chamadas bloqueadas imediatamente, fallback executado → HALF_OPEN após 30 segundos de espera
HALF_OPEN Sondagem — 3 chamadas de teste permitidas → CLOSED se as 3 tiverem sucesso; → OPEN se qualquer uma falhar

Configuração planejada

application.yml

resilience4j:
  circuitbreaker:
    instances:
      whisper:
        slidingWindowSize: 10
        failureRateThreshold: 50          # % de falhas para abrir
        waitDurationInOpenState: 30s
        permittedNumberOfCallsInHalfOpenState: 3
        registerHealthIndicator: true     # expõe no /actuator/health

  retry:
    instances:
      whisper:
        maxAttempts: 3
        waitDuration: 500ms
        enableExponentialBackoff: true
        exponentialBackoffMultiplier: 2   # 500ms → 1s → 2s
        retryExceptions:
          - com.example.diospeechai.transcription.exception.TranscriptionException

SpeechToTextClient.java

// Ordem das anotações importa:
// Retry executa primeiro → tenta N vezes → depois CircuitBreaker decide
@Retry(name = "whisper")
@CircuitBreaker(name = "whisper", fallbackMethod = "fallback")
public WhisperResponse transcribe(MultipartFile file) {
    // ... WebClient call ...
}

private WhisperResponse fallback(MultipartFile file, Exception ex) {
    throw new TranscriptionException(
        "Whisper indisponível — tente novamente em instantes", ex
    );
}

Métricas de resiliência ⏳ v3.3.0

Resilience4j integra automaticamente com Micrometer. As métricas aparecerão no Prometheus sem código adicional.

MétricaDescrição
resilience4j_circuitbreaker_state Estado atual: 0=CLOSED · 1=OPEN · 2=HALF_OPEN
resilience4j_circuitbreaker_calls_total Chamadas por tipo: successful, failed, not_permitted (OPEN), slow
resilience4j_retry_calls_total Tentativas de retry por resultado: successful_with_retry, failed_with_retry

Queries Prometheus

# Estado do circuit breaker (0=CLOSED, 1=OPEN, 2=HALF_OPEN)
resilience4j_circuitbreaker_state{name="whisper"}

# Taxa de chamadas não-permitidas (circuito aberto)
rate(resilience4j_circuitbreaker_calls_total{
  name="whisper", kind="not_permitted"}[1m])

# Taxa de chamadas que precisaram de retry
rate(resilience4j_retry_calls_total{
  name="whisper", kind="successful_with_retry"}[5m])
