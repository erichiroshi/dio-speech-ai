## Por que JWT?

JWT (JSON Web Token) é um token auto-contido: ele carrega as informações do usuário (subject, roles, expiração) assinadas digitalmente. O servidor não precisa consultar um banco de dados para validar o token — basta verificar a assinatura com o secret.

Isso é essencial para APIs stateless: sem sessão HTTP, sem cookie, sem estado no servidor. Cada requisição chega com o token, o token é validado, a requisição é processada ou negada.

---

## HS256 vs RS256

HS256 (HMAC-SHA256) usa um secret simétrico: o mesmo segredo assina e verifica o token. É mais simples e mais rápido.

RS256 usa par de chaves assimétricas (RSA): a chave privada assina, a chave pública verifica. Permite que outros serviços verifiquem tokens sem conhecer o segredo. Para um projeto monolítico como este, HS256 é suficiente — a troca para RS256 seria o passo seguinte se múltiplos serviços precisassem validar tokens independentemente.

---

## Por que Nimbus JOSE+JWT?

O Spring Security OAuth2 Resource Server suporta JWT nativamente, mas requer mais configuração e dependências. Para este projeto, o Nimbus JOSE+JWT (`com.nimbusds:nimbus-jose-jwt`) é mais direto: uma biblioteca focada em JWT com API clara para assinar e verificar.

O Spring Security já inclui o Nimbus como dependência transitiva — não há overhead adicional.

---

## O JwtAuthFilter

```
Requisição chega
    │
    ├── Sem header Authorization → passa sem autenticação
    │   (endpoints públicos aceitam; endpoints protegidos rejeitam com 401)
    │
    └── Com "Bearer <token>"
          ├── Token válido → popula SecurityContext com username e roles
          └── Token inválido/expirado → limpa SecurityContext, deixa seguir
                                        (Spring Security rejeita com 401)
```

O filtro não lança exceção em caso de token inválido — ele limpa o contexto e deixa a requisição seguir. O Spring Security, ao ver o contexto vazio em um endpoint protegido, retorna 401 automaticamente.

---

## SecurityConfig — decisões

**STATELESS**: sem sessão HTTP. Cada requisição deve trazer o token. Não há `HttpSession` criada — reduz memória e elimina problemas de consistência entre instâncias.

**CSRF desabilitado**: CSRF (Cross-Site Request Forgery) é um ataque que explora sessões HTTP. Sem sessão, não há CSRF. Desabilitar evita a necessidade de enviar um token CSRF em cada requisição.

**Endpoints públicos**: `/actuator/health` (healthcheck do Docker Compose), `/actuator/prometheus` (scraping do Prometheus) e `/auth/token` (obter token). Todos os outros requerem autenticação.

---

## AuthController — apenas para desenvolvimento

`POST /auth/token` aceita qualquer username sem validar senha. Isso é intencional para desenvolvimento e testes — não há banco de usuários implementado. Em produção real, esse endpoint seria substituído por integração com Keycloak, Auth0, ou similar.

```bash
TOKEN=$(curl -s -X POST http://localhost:8080/auth/token \
  -H 'Content-Type: application/json' \
  -d '{"username":"user","password":"any"}' | jq -r .token)

curl -H "Authorization: Bearer $TOKEN" \
  -F "file=@audio.wav;type=audio/wav" \
  http://localhost:8080/api/transcriptions
```

---

## Variáveis de ambiente

| Variável | Padrão | Produção |
|---|---|---|
| `JWT_SECRET` | inseguro (hardcoded) | `openssl rand -hex 32` |
| `JWT_EXPIRATION_HOURS` | `8` | definir conforme política de sessão |

O secret hardcoded no `application.yml` é deliberadamente rotulado como inseguro. Em produção, **sempre** usar variável de ambiente com um secret de pelo menos 256 bits.

---

## Trade-offs

| Decisão | Alternativa | Por que esta |
|---|---|---|
| HS256 | RS256 | Simples; adequado para monolito; RS256 para quando múltiplos serviços precisarem verificar |
| Nimbus direto | Spring Security OAuth2 Resource Server | Menos dependências; mais controle sobre o fluxo de validação |
| Filtro não lança em token inválido | Lançar 401 diretamente | Deixar o Spring Security centralizar a política de rejeição |
| CSRF desabilitado | CSRF habilitado | API stateless com JWT não tem vulnerabilidade de CSRF |

# v3.5.0 — Testes de integração (Testcontainers)

## O que foi feito

Cobertura de testes de integração com infraestrutura real: Redis via Testcontainers e Speaches simulado via MockWebServer. Os testes validam o fluxo completo de ponta a ponta.

### Arquivos alterados/criados

| Arquivo | Tipo | O que mudou |
|---|---|---|
| `build.gradle` | modificado | + Testcontainers BOM + redis container + mockwebserver, version `3.5.0` |
| `TranscriptionIntegrationTest.java` | novo | 6 cenários de integração |

---

## Por que Testcontainers?

Testes de integração com mocks de Redis (`@MockBean RedisTemplate`) testam o código, não o comportamento real. Testcontainers sobe um container Docker real de Redis durante o teste e o derruba ao finalizar. O teste executa contra Redis real, com serialização real, com TTL real.

A alternativa seria um servidor Redis embarcado (ex: `embedded-redis`). O problema é que servidores embarcados não têm paridade total com Redis real — versões, comandos suportados, comportamento de persistência podem divergir.

---

## MockWebServer para o Speaches

O Speaches não tem um container Testcontainers — sobe a GPU e leva minutos. `MockWebServer` (OkHttp) resolve isso: sobe um servidor HTTP real na porta disponível e permite enfileirar respostas.

```java
mockSpeaches.enqueue(new MockResponse()
    .setBody("{\"text\":\"audio transcrito\"}")
    .addHeader("Content-Type", "application/json"));
```

O `WHISPER_BASE_URL` é sobrescrito via `@DynamicPropertySource` para apontar para `localhost:<porta do MockWebServer>`. A aplicação não sabe que está falando com um mock.

---

## @DynamicPropertySource

Permite sobrescrever propriedades do Spring em tempo de execução dos testes — depois que os Testcontainers subiram e as portas foram alocadas:

```java
@DynamicPropertySource
static void properties(DynamicPropertyRegistry registry) {
    registry.add("spring.data.redis.host", redis::getHost);
    registry.add("spring.data.redis.port", () -> redis.getMappedPort(6379));
    registry.add("whisper.base-url",
            () -> "http://localhost:" + mockSpeaches.getPort());
}
```

Isso evita hardcodar portas e permite que o Testcontainers aloque portas dinamicamente (evitando conflitos).

---

## Os 6 cenários cobertos

| Cenário | O que valida |
|---|---|
| JWT ausente | Spring Security rejeita com 401 antes de chegar no controller |
| JWT inválido | JwtAuthFilter rejeita, SecurityContext vazio, Spring Security 401 |
| Content-Type inválido (PDF) | Validação no service retorna 400 |
| Cache miss — 1ª chamada | Speaches é chamado, resposta sem `cached` |
| Cache hit — 2ª chamada igual | Redis responde, `cached=true`, Speaches não chamado |
| CircuitBreaker — 4 falhas → 503 | CB abre após threshold, fallback retorna 503 |

O cenário do CircuitBreaker usa `@DynamicPropertySource` para configurar uma janela pequena (4 chamadas) e threshold de 50%, tornando o teste rápido e previsível.

---

## Trade-offs

| Decisão | Alternativa | Por que esta |
|---|---|---|
| Testcontainers Redis | Embedded Redis | Paridade total com Redis real; mesmo comportamento de serialização |
| MockWebServer para Speaches | Container Speaches no teste | Speaches com GPU leva minutos; MockWebServer é instantâneo |
| `@DynamicPropertySource` | `application-test.yml` com portas fixas | Portas dinâmicas evitam conflito; mais robusto em CI |
| `@SpringBootTest` completo | `@WebMvcTest` por camada | Testa a integração real entre todas as camadas, não camadas isoladas |
