# v2.2.0 — Logs estruturados (JSON + MDC)

## O que foi feito

Substituição dos logs texto plano por logs JSON estruturados, com campos de contexto (MDC) injetados automaticamente em cada requisição. O objetivo era transformar logs de "texto para ler" em "dados para consultar".

## O que é MDC?

MDC (Mapped Diagnostic Context) é um mapa de pares chave-valor mantido pelo SLF4J em `ThreadLocal`. Qualquer campo colocado no MDC fica disponível para **todos os logs emitidos na mesma thread** até ser removido, sem precisar passar o valor explicitamente para cada método.

É a forma padrão de enriquecer logs com contexto de requisição em aplicações Java.

---

## Por que logs JSON?

Logs em texto plano como `2026-04-11 INFO TranscriptionService - Transcrição concluída` são fáceis de ler no terminal, mas difíceis de consultar em volume. Para responder "qual foi o tempo médio das transcrições de arquivos acima de 400KB hoje?" com texto plano, seria necessário regex e awk. Com JSON, é uma query no Loki, Elasticsearch ou qualquer agregador.

Cada campo MDC vira um campo de primeiro nível no JSON:

```json
{
  "@timestamp": "2026-04-11T12:00:00.123Z",
  "level": "INFO",
  "logger": "TranscriptionService",
  "message": "Transcrição concluída | chars=142 | size=461842bytes",
  "requestId": "a3f2c1d0-7f3e-4b2a-9c1d-e8f5a6b7c8d9",
  "fileName": "audio.wav",
  "fileSizeBytes": "461842",
  "whisperModel": "Systran/faster-whisper-small",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "spanId": "00f067aa0ba902b7",
  "app": "dio-speech-ai",
  "version": "2.2.0"
}
```

## logback-spring.xml — dois perfis

O arquivo usa `<springProfile>` para alternar o comportamento sem mudar código:

- **`!dev` (padrão/prod)**: `LogstashEncoder` serializa tudo em JSON, campos MDC como campos raiz
- **`dev`**: `PatternLayoutEncoder` com texto colorido e `requestId`/`fileName` inline — mais legível no terminal durante desenvolvimento

A diferença é apenas de formato. Os mesmos campos são capturados nos dois modos.

---

## MdcLoggingFilter

`OncePerRequestFilter` com `@Order(1)` — executa antes de qualquer outro filtro.

Popula três campos ao início de cada requisição:
- `requestId`: UUID aleatório. Único por requisição. Propagado no header `X-Request-Id` da resposta.
- `httpMethod`: GET, POST, etc.
- `requestUri`: path da requisição

O `MDC.clear()` no bloco `finally` é crítico: MDC usa `ThreadLocal`. Se não for limpo, o estado de uma requisição pode vazar para a próxima em pools de threads (o Tomcat reutiliza threads).

---

## requestId vs traceId

Os dois coexistem propositalmente:

- `requestId` é gerado pelo `MdcLoggingFilter` e retornado no header `X-Request-Id` e no body do `ProblemDetail`. É o identificador que o cliente recebe e pode usar para abrir um chamado de suporte.
- `traceId` é gerado pelo OpenTelemetry/Micrometer Tracing (adicionado na v2.7.0) e serve para correlacionar spans entre serviços no Zipkin. É hexadecimal de 32 chars — menos legível para usuário final.

Remover um dos dois seria perder uma camada de rastreabilidade. O `requestId` é para rastreabilidade externa (cliente ↔ suporte). O `traceId` é para rastreabilidade interna (Zipkin, correlação entre spans).

## Campos MDC por camada

| Campo | Quem popula | Quando |
|---|---|---|
| `requestId` | MdcLoggingFilter | início de toda requisição HTTP |
| `httpMethod` | MdcLoggingFilter | início de toda requisição HTTP |
| `requestUri` | MdcLoggingFilter | início de toda requisição HTTP |
| `fileName` | TranscriptionService | início do `transcribe()` |
| `fileSizeBytes` | TranscriptionService | início do `transcribe()` |
| `whisperModel` | SpeechToTextClient | antes da chamada HTTP ao Speaches |
| `traceId`, `spanId` | Micrometer Tracing (automático) | v2.7.0 |

O `TranscriptionService` remove `fileName`, `fileSizeBytes` e `whisperModel` no `finally`, mas não remove `requestId` — esse é responsabilidade do `MdcLoggingFilter`.

## Trade-offs

| Decisão | Alternativa | Por que esta |
|---|---|---|
| logstash-logback-encoder | Jackson manual no appender | Encoder já trata escaping, timestamps ISO, campos MDC como raiz automaticamente |
| `springProfile` no logback-spring.xml | dois arquivos (logback-prod.xml, logback-dev.xml) | Um arquivo só, sem risco de esquecer de sincronizar os dois |
| `MDC.clear()` no finally do filtro | `MDC.remove()` campo a campo | `clear()` garante limpeza total; campos específicos poderiam ser esquecidos em refatorações futuras |
| requestId no ProblemDetail | sem requestId no body de erro | Permite que o cliente correlacione um erro 4xx/5xx com os logs do servidor sem acesso ao Zipkin |
