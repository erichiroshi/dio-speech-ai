# v2.3.0 — Redis no Docker Compose

## O que foi feito

Infraestrutura de cache: subir o Redis nos dois composes e configurar o Spring para se conectar a ele. Nenhuma lógica de cache ainda — isso é a v2.4.0. ## Por que Redis?

Redis é um banco de dados em memória com estrutura de dados chave-valor. Para o caso de uso aqui — cachear o resultado de uma operação cara e determinística — é a escolha padrão da indústria por três razões:

1. **Latência**: acesso em memória, respostas em sub-milissegundo
2. **TTL nativo**: toda chave pode ter um tempo de expiração sem código adicional
3. **Persistência opcional**: com AOF (Append Only File), as chaves sobrevivem a reinicializações do container

A alternativa mais simples seria cache em memória local (Caffeine, `@Cacheable` do Spring). O problema é que cache local não é compartilhado entre instâncias: se a aplicação escalar horizontalmente para duas instâncias, cada uma teria seu próprio cache. Com Redis centralizado, todas as instâncias compartilham o mesmo cache.

## RedisConfig — por que configurar manualmente?

O Spring Boot autoconfigura um `RedisTemplate<Object, Object>` por padrão, mas esse template usa serialização Java nativa (`JdkSerializationRedisSerializer`). Isso tem dois problemas:

1. O valor armazenado no Redis é binário ilegível — impossível inspecionar com `redis-cli`
2. A deserialização depende da mesma versão da classe — uma mudança em `TranscriptionResponse` pode corromper entradas existentes no cache

A configuração manual define:
- **Chave**: `StringRedisSerializer` — a chave fica como texto puro: `transcription:3a14c5...`
- **Valor**: `JacksonJsonRedisSerializer<TranscriptionResponse>` — o valor fica como JSON legível

Isso permite inspecionar o cache diretamente:
```bash
docker exec -it redis redis-cli get "transcription:3a14c5038f8ff..."
# {"text":"testando o áudio...","fileSizeBytes":461842}
```

### Por que JacksonJsonRedisSerializer e não Jackson2JsonRedisSerializer?

O `Jackson2JsonRedisSerializer` foi depreciado no Spring Data Redis 3.x. O `JacksonJsonRedisSerializer` é o substituto direto com a mesma API — a única diferença é o nome.

## Separação prod vs dev

**Prod** (`docker-compose.yml`):
- Volume `redis_data` com persistência AOF (`redis-server --appendonly yes`)
- `depends_on: redis: condition: service_healthy` na API — garante que o Redis passou no healthcheck antes de a aplicação subir
- Porta 6379 mapeada apenas para inspeção local (não deveria ser exposta em prod real)

**Dev** (`docker-compose.dev.yml`):
- Sem volume persistente — dados apagados a cada `docker compose down`
- Porta 6379 exposta no host para que a aplicação local (`./gradlew bootRun`) conecte via `localhost:6379`
- Sem persistência intencional: facilita testes que precisam de cache limpo

## Saúde do Redis no Actuator

Com `spring-boot-starter-data-redis`, o Spring Boot autoconfigura um `RedisHealthIndicator`. O `/actuator/health` passa a incluir:

```json
{
  "status": "UP",
  "components": {
    "redis": {
      "status": "UP",
      "details": { "version": "8.0.0" }
    }
  }
}
```

Se o Redis cair, o `status` da aplicação fica `DOWN`. O healthcheck do Docker Compose usa isso — se a API reportar `DOWN`, o Compose a considera não saudável.

## Trade-offs

| Decisão | Alternativa | Por que esta |
|---|---|---|
| Redis centralizado | Cache em memória (Caffeine) | Compartilhado entre instâncias; sobrevive a restart da API |
| `JacksonJsonRedisSerializer` tipado | `GenericJackson2JsonRedisSerializer` | Sem type info no JSON — mais limpo, mais interoperável com outros serviços |
| Serialização JSON | Serialização Java nativa | Legível via redis-cli; tolerante a mudanças na classe |
| Persistência AOF em prod | Sem persistência | Cache aquecido sobrevive a restart do container; sem TTL manual |
| redis:8-alpine | redis:latest | Versão fixa e explícita; imagem alpine é menor (~30MB vs ~100MB) |
