## Decisões e trade-offs

### Por que áudio em Base64 e não bytes diretamente?

RabbitMQ transmite mensagens em formato AMQP. Ao usar JSON como formato
de serialização (Jackson2JsonMessageConverter), o campo de áudio precisa
ser texto — `byte[]` em JSON é representado como Base64 automaticamente
pelo Jackson, mas a legibilidade e o controle explícito ficam melhores
com um campo `String audioBase64`.

Produtores externos (outros serviços) simplesmente codificam o áudio em
Base64 antes de publicar. O consumer decodifica antes de criar o `TranscribeCommand`.

**Trade-off:** Base64 aumenta o tamanho da mensagem em ~33%. Para áudios
pequenos (< 5MB) é aceitável. Para volumes altos, considerar armazenar o
áudio em S3 e enviar apenas a URL na mensagem — mas isso é complexidade
prematura para este projeto.

### Por que `requestId` é opcional?

O `requestId` é para rastreabilidade — permite correlacionar o pedido na fila
com os logs da transcrição via MDC. Produtores que não têm ID próprio podem
omitir o campo; o consumer usa `"unknown"` como fallback.

### Separação de comportamento de falha

```java
} catch (TranscriptionException ex) {
    // Validação de domínio (ex: Content-Type inválido)
    // Não faz sentido retentar — DLQ imediatamente
    throw ex;
} catch (Exception ex) {
    // Falha técnica (Redis, Whisper)
    // Spring AMQP retenta 3x → DLQ
    throw ex;
}
```

A distinção é importante: retentar um pedido com Content-Type inválido
é desperdiçar tentativas — ele sempre vai falhar. Retentar uma falha técnica
faz sentido — o Redis pode ter caído momentaneamente.

**Trade-off:** `TranscriptionException` é usada tanto para validação quanto
para falhas de I/O no Whisper. Idealmente, existiria uma `ValidationException`
separada para não retentar. Por ora, toda `TranscriptionException` vai direto
para DLQ — inclui falhas de I/O que poderiam ser recuperáveis. Melhoria futura.

### O consumer não retorna nada

O `TranscribeAudioUseCase` já chama `eventPort.publish()` internamente — que
publica o `TranscriptionCompletedEvent` na exchange. O consumer não precisa
se preocupar com a resposta: o produtor original assina a exchange
`transcription.events` para receber o resultado.

Este padrão é fire-and-forget: o produtor publica o pedido e assina o evento
de conclusão em exchanges separadas.
