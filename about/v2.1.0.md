## Por que Micrometer?

O Spring Boot Actuator já estava no projeto desde a v1.0.0 (usado no healthcheck do Docker). O Micrometer é a camada de abstração de métricas que o Actuator usa internamente. Adicionar `micrometer-registry-prometheus` faz com que o Micrometer serialize todas as métricas coletadas no formato que o Prometheus entende, e as exponha no endpoint `/actuator/prometheus`.

A vantagem da abstração é que o código de métricas (`TranscriptionMetrics`) não sabe que o destino é o Prometheus. Se amanhã o destino mudar para Datadog ou InfluxDB, troca-se a dependência do `build.gradle` e o código de instrumentação permanece intacto.

---

## Por que Prometheus?

Prometheus usa um modelo de **pull**: ele é quem vai buscar as métricas na API a cada intervalo configurado (10s no projeto), não o contrário. Isso simplifica a configuração da aplicação — ela só precisa expor o endpoint, sem precisar saber o endereço de nenhum coletor.

A alternativa seria push (a API envia métricas para um coletor). O modelo pull é mais adequado aqui porque: o Prometheus tem controle sobre a taxa de coleta, consegue detectar quando a aplicação morreu (simplesmente para de responder), e a configuração fica centralizada no `prometheus.yml`.

## A classe TranscriptionMetrics

Centralizou todos os instrumentos Micrometer em um único lugar, injetado no `TranscriptionService`. Três tipos de instrumento foram usados:

**Counter** para `transcription.requests.total` com tag `status=success|error`. A tag permite calcular a taxa de erros no Prometheus sem precisar de duas métricas separadas:
```
rate(transcription_requests_total{status="error"}[1m])
  /
rate(transcription_requests_total[1m])
```

**Timer** para `transcription.whisper.duration`. Um Timer no Micrometer registra automaticamente contagem, soma, máximo e — quando `publishPercentileHistogram()` está ativado — um histograma de buckets que permite calcular percentis no lado do Prometheus (p50, p95, p99). Isso é mais preciso do que percentis pré-calculados do lado da aplicação.

**DistributionSummary** para `transcription.file.size.bytes`. Semelhante ao Timer, mas para valores de negócio (não duração). Permite saber a distribuição dos tamanhos de arquivo enviados ao longo do tempo.

O método `recordWhisperCall(Supplier<T>)` encapsula a chamada ao Whisper dentro do Timer, garantindo que o tempo seja medido mesmo em caso de exceção.

## Remoção de processingTimeMs

O `TranscriptionResponse` tinha o campo `processingTimeMs` calculado com `System.currentTimeMillis()`. Esse campo foi removido porque:

1. Era calculado no `TranscriptionService`, incluindo o tempo de validação — não era só o tempo do Whisper
2. Tinha precisão de milissegundos inteiros, sem percentis ou histograma
3. O Timer do Micrometer faz isso com muito mais riqueza: buckets, p50/p95/p99, agregação no tempo

Clientes que precisarem do tempo de processamento usam `GET /actuator/metrics/transcription.whisper.duration`.

## Perfil dev vs prod

O `prometheus-dev.yml` aponta para `host.docker.internal:8080` porque em modo dev a aplicação roda fora do Docker. O `prometheus.yml` aponta para `dio-speaches-ai:8080` porque em modo prod todos os serviços estão na mesma rede Docker.

---

## Trade-offs

| Decisão | Alternativa considerada | Por que esta |
|---|---|---|
| Percentis via histograma (`publishPercentileHistogram`) | Percentis pré-calculados (`publishPercentiles`) | Histograma permite calcular qualquer percentil no Prometheus; pré-calculados são fixos e consomem mais memória no Prometheus |
| Tag única `status=success\|error` | Dois contadores separados | Uma métrica com tags é mais flexível para queries e dashboards |
| Pull (Prometheus busca) | Push (app envia) | Pull detecta morte da aplicação; configuração centralizada |
| Timer para Whisper | `System.currentTimeMillis()` | Timer é thread-safe, tem suporte a percentis, e não polui a resposta HTTP |
