## Decisões e trade-offs

### Por que novo domínio `analysis/` e não dentro de `transcription/`?

Análise e transcrição são contextos diferentes com responsabilidades distintas:
- `transcription/` converte áudio em texto
- `analysis/` interpreta o texto transcrito

A comunicação é via `audioHash` — um value object compartilhado, não um acoplamento direto.
Isso permite evoluir cada contexto independentemente e eventualmente extrair análise
para um microserviço separado.

### Por que `LanguageModelPort` recebe apenas `String prompt`?

O port de saída é a fronteira mais fina possível. O use case monta o prompt completo
com o contexto necessário — o adapter só precisa chamar o LLM e retornar o texto.

Se amanhã precisarmos de parâmetros adicionais (temperatura, max_tokens), isso
vai para `OllamaProperties` ou para um objeto `LlmRequest` — sem mudar o contrato
do port imediatamente.

### Por que o controller busca a transcrição via `TranscriptionCachePort`?

O controller do domínio `analysis/` precisa do texto transcrito para passar ao use case.
Em vez de criar uma nova abstração, reutilizamos o `TranscriptionCachePort` já existente.

**Trade-off:** cria um acoplamento entre o domínio `analysis/` e o port de `transcription/`.
Em Clean Architecture estrita, `analysis/` não deveria conhecer ports de `transcription/`.
Para este projeto o acoplamento é aceitável — é entre um adapter de entrada e
um port de saída de outro domínio, não entre domínios.

**Alternativa mais pura:** criar um port próprio `TranscriptionTextPort` em `analysis/domain/port/out/`
implementado por um adapter que delega ao Redis. Faria sentido se o projeto crescesse.

### Por que `@ConditionalOnMissingBean` no `NoOpSummaryStoreAdapter`?

Em vez de `@Primary` no adapter real, usamos `@ConditionalOnMissingBean` no no-op.
Quando o `RedisSummaryStoreAdapter` (v10.2.0) for registrado com o bean name
`redisSummaryStoreAdapter`, o no-op não é criado. Mais explícito do que `@Primary`.

### Prompt em português

Modelos como `llama3.2:3b` funcionam razoavelmente bem em português.
O prompt instrui explicitamente: "Responda APENAS com o resumo, sem introduções."
Isso evita respostas como "Claro! Aqui está o resumo: ..." que poluem a saída.

**Trade-off:** modelos menores às vezes ignoram a instrução e adicionam prefixos.
Uma melhoria seria pós-processar a resposta para remover prefixos comuns.

### Spring AI `ChatClient` vs `OllamaChatModel` diretamente

`ChatClient` é a API de alto nível do Spring AI — fluent interface, suporte a
advisors, chat memory, RAG. Usamos via `ChatClient.builder(ollamaChatModel).build()`.

`OllamaChatModel` diretamente seria mais baixo nível e quebraria ao trocar de
provedor. `ChatClient` é a abstração correta.
