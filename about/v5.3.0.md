## release.yml

### Por que re-taguear e não rebuildar?

O `docker.yml` já buildou e publicou a imagem com a tag `latest` quando
o commit chegou na `main`. O `release.yml` apenas cria um alias com versão:

```bash
docker pull erichiroshi/dio-speech-ai:latest
docker tag  erichiroshi/dio-speech-ai:latest erichiroshi/dio-speech-ai:5.3.0
docker push erichiroshi/dio-speech-ai:5.3.0
```

Rebuildar seria desperdiçar tempo e energia: o binário é exatamente o mesmo.
Re-taguear garante que `v5.3.0` aponta para o mesmo SHA que foi testado
e validado pelo `ci.yml`.

### generate_release_notes: true

```yaml
uses: softprops/action-gh-release@v2
with:
  generate_release_notes: true
```

O GitHub gera release notes automaticamente a partir dos commits entre a
tag anterior e a atual. Isso funciona melhor com Conventional Commits
(`feat:`, `fix:`, `refactor:`, etc.) — os commits são agrupados
automaticamente por tipo.

### O fluxo completo de uma release

```
1. ./gradlew build                  → testes passam + cobertura ≥ 70%
2. git tag -a v5.3.0 -m "..."
3. git push origin v5.3.0

Automaticamente (GitHub Actions):
4. release.yml  → re-tag Docker Hub + GitHub Release
5. docs.yml     → gera PDF + anexa ao release
```

## docs.yml

### Por que um arquivo separado do README.md?

O `README.md` é um documento de portfólio: tem emojis, badges Shields.io,
HTML inline, seções visuais para GitHub. Pandoc + xelatex não renderiza
isso adequadamente — emojis viram quadrados, badges quebram, HTML inline
gera erros de LaTeX.

O `readme_pdf.md` é um documento técnico limpo: Markdown puro, tabelas
simples, blocos de código, sem nenhum elemento que quebre na conversão.

### Pandoc + xelatex

```bash
pandoc readme_pdf.md -o dio-speech-ai.pdf \
  --pdf-engine=xelatex \
  --toc --toc-depth=2 \
  -V mainfont="DejaVu Sans" \
  -V monofont="DejaVu Sans Mono"
```

`xelatex` suporta Unicode nativamente — necessário para acentos do português
(`ã`, `ç`, `é`). `pdflatex` quebraria com esses caracteres sem configuração
adicional complexa.

A tabela de conteúdo (`--toc`) é gerada automaticamente a partir dos
headings do Markdown. Com 2 níveis de profundidade (`--toc-depth=2`),
cobre `##` e `###` sem ficar muito granular.

### Disparo duplo

```yaml
on:
  push:
    branches: [ "main" ]
    paths:
      - 'readme_pdf.md'    # atualização de conteúdo
  push:
    tags:
      - 'v*'               # toda release
```

O primeiro disparo garante que o PDF é atualizado sempre que o documento
técnico muda, independente de release. O segundo garante que toda release
tem o PDF anexado.

## readme_pdf.md — decisões de conteúdo

### O que incluir

- Requisitos de ambiente
- Quick start (dev e prod)
- Todos os endpoints com exemplos de request/response
- Todas as variáveis de ambiente com valores padrão
- Tabela de serviços Docker Compose com portas
- Explicação do cache e da resiliência
- Resumo da observabilidade
- Resumo do CI/CD
- Links

### O que não incluir

- Emojis (quebram no LaTeX)
- Badges (imagens externas — quebram)
- HTML inline (não é Markdown puro)
- Detalhes de implementação (fica no `about/`)
- Histórico de versões (fica no `VERSIONING.md`)

### Regra de atualização

O `readme_pdf.md` é atualizado em toda fase que mudar **comportamento externo**:
novo endpoint, novo campo na resposta, nova variável de ambiente, mudança
na forma de rodar o projeto.

Mudanças puramente internas (refatoração, testes, CI) não precisam atualizar
o PDF.

Qualquer regressão introduzida por uma refatoração seria descoberta manualmente.

qualidade. A Fase 7 (arquitetura hexagonal) vai mover arquivos e renomear
pacotes em 6 commits — o pipeline verde em cada step é a rede de segurança
que torna essa refatoração confiável.
