## Decisões e trade-offs

### NotifyUseCase: injeção de List<NotificationPort>

O Spring injeta automaticamente todos os beans que implementam `NotificationPort`.
O use case monta um `Map<NotificationChannel, NotificationPort>` na construção:

```java
public NotifyUseCase(List<NotificationPort> ports) {
    this.adapters = ports.stream()
        .collect(Collectors.toMap(NotificationPort::channel, Function.identity()));
}
```

**Vantagem:** para adicionar um novo canal, basta criar um adapter que implemente
`NotificationPort`. O `NotifyUseCase` descobre automaticamente sem nenhuma alteração.

**Trade-off:** se dois adapters declararem o mesmo canal, o `Collectors.toMap`
lançará `IllegalStateException` na inicialização — melhor falhar cedo do que
sobrescrever silenciosamente.

### Destinatário e canal via configuração

O `TranscriptionCompletedConsumer` usa `@Value` para ler destinatário e canal.
Isso é uma simplificação deliberada — em produção real, o evento carregaria
o destinatário (e-mail ou telefone do usuário) e o canal preferido.

Para esta fase do portfólio, configurar via variável de ambiente já demonstra
o padrão completo. A evolução futura seria adicionar esses campos ao
`TranscriptionCompletedEvent` e ao domínio do usuário.

### Por que novo pacote `notification/` e não dentro de `transcription/`?

Notificação é um domínio separado — tem suas próprias regras, seus próprios
adapters e não depende dos detalhes de como a transcrição foi feita.
O acoplamento é apenas pelo evento `TranscriptionCompletedEvent`, que é um
DTO público do adapter de saída de transcrição.

Manter domínios separados facilita extrair notificação para um microserviço
independente no futuro — o pacote já tem fronteiras claras.
