# v2.5.0 — Métricas de cache (hit/miss)

## O que foi feito

Adição de dois contadores ao `TranscriptionMetrics` para rastrear cache hits e misses. Sem esses contadores, o cache era invisível para o Prometheus e o Grafana.

### Arquivos alterados

| Arquivo | Tipo | O que mudou |
|---|---|---|
| `build.gradle` | modificado | version `2.5.0` |
| `TranscriptionMetrics.java` | modificado | + `cacheHitCounter` e `cacheMissCounter` |

---

## Por que métricas de cache?

O cache estava funcionando, mas sem visibilidade. Não era possível responder: qual é a taxa de reaproveitamento? Quantas chamadas ao Whisper foram evitadas? O cache está aquecendo ao longo do tempo?

Com os dois contadores, o Prometheus consegue calcular o cache hit ratio em tempo real:

```promql
sum(rate(transcription_cache_total{result="hit"}[5m]))
  /
(sum(rate(transcription_cache_total{result="hit"}[5m]))
 + sum(rate(transcription_cache_total{result="miss"}[5m])) + 0.0001)
```

O `+ 0.0001` evita divisão por zero quando não há tráfego.

## Por que sum() antes da divisão?

Métricas com tags diferentes (`result="hit"` e `result="miss"`) são séries distintas no Prometheus. Dividir dois vetores diferentes sem agregação gera `No data` no Grafana — o Prometheus não sabe como parear as séries. O `sum()` colapsa cada série em um escalar antes da divisão.

# v2.6.0 — Grafana + dashboards

## O que foi feito

Adição do Grafana aos composes com provisioning automático: datasource Prometheus + dashboard JSON carregado na inicialização. Nenhuma configuração manual necessária.

### Arquivos criados/alterados

| Arquivo | Tipo | O que mudou |
|---|---|---|
| `build.gradle` | modificado | version `2.6.0` |
| `docker-compose.yml` | modificado | + serviço `grafana` |
| `docker-compose.dev.yml` | modificado | + serviço `grafana` |
| `monitoring/grafana/provisioning/datasources/prometheus.yml` | novo | datasource |
| `monitoring/grafana/provisioning/dashboards/dashboards.yml` | novo | provider de dashboards |
| `monitoring/grafana/dashboards/dio-speech-ai.json` | novo | dashboard com 9 painéis |

---

## Por que provisioning automático?

Sem provisioning, o Grafana sobe com a tela de configuração em branco. O usuário precisa: criar o datasource, importar o dashboard, configurar as queries. Isso é trabalho manual repetido a cada `docker compose down -v`.

Com provisioning, os arquivos em `monitoring/grafana/provisioning/` são lidos na inicialização:
- `datasources/prometheus.yml`: cadastra o Prometheus como datasource padrão
- `dashboards/dashboards.yml`: instrui o Grafana a carregar JSONs do diretório `dashboards/`

O container sobe e o dashboard está pronto, sem intervenção.

## Os 9 painéis do dashboard

| Seção | Painel | Métrica |
|---|---|---|
| Requisições | Taxa req/s | `http_server_requests_seconds_count` |
| Requisições | Taxa de erros | `transcription_requests_total{status=error}` |
| Requisições | Cache hit ratio | `transcription_cache_total` |
| Requisições | Whisper p99 | `transcription_whisper_duration_seconds_bucket` |
| Requisições | Tamanho médio | `transcription_file_size_bytes` |
| Latência Whisper | p50/p95/p99 (timeseries) | histograma Whisper |
| Latência Whisper | Throughput por status | success/error por minuto |
| Cache Redis | Hit vs miss por minuto | `transcription_cache_total` |
| Cache Redis | Hit ratio (gauge) | ratio calculado |

O dashboard da v3.3.0 adiciona a seção de resiliência com 3 painéis adicionais.

## Trade-offs

| Decisão | Alternativa | Por que esta |
|---|---|---|
| Provisioning via arquivos | Configuração manual | Reproducível; versionado no Git; zero cliques |
| Dashboard como JSON no repositório | Dashboard criado na UI | Histórico de versões, diff, revisão em PR |
| Grafana no compose de dev | Grafana separado | Dev tem visibilidade completa sem infraestrutura adicional |

# v2.7.0 — Tracing Zipkin (OpenTelemetry)

## O que foi feito

Terceiro pilar de observabilidade: tracing distribuído. Cada requisição gera um trace com spans para cada operação — HTTP recebido, chamada ao Whisper, acesso ao Redis. Todos os spans de uma requisição são correlacionados por um `traceId` único.

### Arquivos alterados/criados

| Arquivo | Tipo | O que mudou |
|---|---|---|
| `build.gradle` | modificado | + `micrometer-tracing-bridge-otel`, `opentelemetry-exporter-zipkin`, `spring-boot-starter-zipkin`, version `2.7.0` |
| `application.yml` | modificado | + `management.tracing` + `zipkin.export.zipkin.endpoint` |
| `docker-compose.yml` | modificado | + serviço `zipkin` |
| `docker-compose.dev.yml` | modificado | + serviço `zipkin` |

---

## Três pilares de observabilidade

| Pilar | Ferramenta | Pergunta que responde |
|---|---|---|
| Métricas | Prometheus + Grafana | "O que está acontecendo em agregado?" |
| Logs | Logback JSON + MDC | "O que aconteceu nessa requisição específica?" |
| Traces | Zipkin + OpenTelemetry | "Onde o tempo foi gasto em cada operação?" |

Sozinhos, cada pilar tem pontos cegos. Juntos, cobrem desde a visão macro (dashboards) até a visão microscópica (cada span de cada requisição).

---

## Por que OpenTelemetry?

OpenTelemetry é o padrão aberto para observabilidade (métricas, logs, traces). A ponte `micrometer-tracing-bridge-otel` conecta o Micrometer (que o Spring Boot usa internamente) ao SDK do OpenTelemetry. O exportador `opentelemetry-exporter-zipkin` converte os spans para o formato que o Zipkin entende.

Essa separação em camadas permite trocar o destino dos traces sem mudar código: substituir o exportador Zipkin por um OTLP (para Jaeger, Grafana Tempo, etc.) é uma linha no `build.gradle`.

Além disso, com `spring-boot-starter-zipkin` as propriedades de configuração são reconhecidas automaticamente pelo autoconfigure do Spring Boot.

---

## traceId nos logs

Com `micrometer-tracing-bridge-otel`, o `traceId` e o `spanId` são injetados automaticamente no MDC pela ponte. Sem nenhuma mudança de código, o log JSON passa a ter:

```json
{
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "spanId":  "00f067aa0ba902b7",
  "requestId": "a3f2c1d0-..."
}
```

O `traceId` conecta os logs ao Zipkin: copie o `traceId` do log, cole na busca do Zipkin, veja o trace completo com todos os spans e durações.

## O que o Zipkin mostra

- **Cache miss**: dois spans — HTTP recebido (span raiz) + WebClient ao Whisper (span filho). É possível ver exatamente quanto tempo cada um levou.
- **Cache hit**: um span — HTTP recebido. O Redis respondeu antes de qualquer chamada sair. O span do Whisper não existe.
- **CircuitBreaker OPEN**: um span curto — a requisição terminou no fallback antes de qualquer chamada externa.

## Trade-offs

| Decisão | Alternativa | Por que esta |
|---|---|---|
| OpenTelemetry via Micrometer bridge | Zipkin SDK direto | Abstração: troca o backend de tracing sem mudar código |
| Sampling 100% | Sampling parcial (0.1) | Em dev, ver todos os traces. Em prod de alta carga, reduzir via `TRACING_SAMPLING=0.1` |
| requestId coexistindo com traceId | Só traceId | requestId retorna ao cliente (header + ProblemDetail); traceId é interno |
