## Decisões e trade-offs

### Adapters genéricos — agnósticos ao provedor

Tanto `SmsNotificationAdapter` quanto `WhatsAppNotificationAdapter` recebem
`baseUrl`, `sendPath` e credenciais via `@ConfigurationProperties`.
Para trocar de Vonage para Twilio: alterar as variáveis de ambiente.

**Trade-off:** um adapter 100% genérico não cobre todos os quirks de um provedor
específico (formato de autenticação, estrutura do payload, webhooks de status).
Para portfólio, a genericidade demonstra Ports & Adapters mais claramente do que
código amarrado ao Twilio.

### MockWebServer — reutilizando a lib do Whisper

O projeto já usa `okhttp3:mockwebserver` para testes do `WhisperAdapter`.
Reutilizar a mesma lib mantém o stack de testes consistente. O `RecordedRequest`
permite inspecionar path, headers e body sem servidor real.

### @Nested — dois adapters em um arquivo de teste

SMS e WhatsApp seguem o mesmo padrão de teste. Organizar com `@Nested` evita
proliferação de arquivos pequenos e mantém coesão temática.

### Padrão para adicionar novo canal

1. Adicionar valor ao enum `NotificationChannel`
2. Criar `XyzProperties` com `@ConfigurationProperties`
3. Criar `XyzNotificationAdapter implements NotificationPort`
4. `channel()` retorna o novo canal
5. Teste com MockWebServer (ou GreenMail para e-mail)

`NotifyUseCase` e `TranscriptionCompletedConsumer` não mudam.
