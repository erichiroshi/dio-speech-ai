## Decisões e trade-offs

### Adapters genéricos (não acoplados a um provedor específico)

Tanto `SmsNotificationAdapter` quanto `WhatsAppNotificationAdapter` são
agnósticos ao provedor — recebem `baseUrl`, `sendPath` e credenciais via
propriedades. Para trocar de Vonage para Twilio (SMS) basta alterar as
variáveis de ambiente. O payload pode precisar de ajuste mínimo, mas o
padrão do adapter não muda.

**Trade-off:** um adapter 100% genérico pode não cobrir todos os quirks
de um provedor específico (autenticação diferente, formato de resposta,
webhooks). Para um MVP e portfólio, a genericidade demonstra o padrão
Ports & Adapters de forma mais clara do que código amarrado ao Twilio.

### MockWebServer — reutilizando a lib já presente

O projeto já usa `okhttp3:mockwebserver` para testes do `WhisperAdapter`.
Reutilizar a mesma lib para testar os adapters de notificação mantém o
stack de testes consistente — sem adicionar WireMock ou outro servidor mock.

```java
server.enqueue(new MockResponse().setResponseCode(200));
adapter.send(request);
RecordedRequest recorded = server.takeRequest();
assertThat(recorded.getPath()).isEqualTo("/v1/sms");
```

O `RecordedRequest` permite inspecionar o que o adapter enviou:
path, headers e body — sem precisar de um servidor real.

### @Nested para organizar testes de dois adapters

Os testes de SMS e WhatsApp ficam no mesmo arquivo (mesma lib, mesmo padrão)
mas organizados em classes `@Nested` separadas. Isso evita proliferação de
arquivos de teste pequenos e mantém a coesão temática.

### WhatsApp: payload Meta Cloud API

O payload gerado é compatível com a Meta Cloud API (WhatsApp Business):
```json
{
  "messaging_product": "whatsapp",
  "to": "5567999999999",
  "type": "text",
  "text": { "body": "Transcrição concluída:\ntexto..." }
}
```
Para usar com Twilio ou outro provedor, o `WhatsAppNotificationAdapter.send()`
precisaria de um payload diferente — justifica criar um adapter por provedor
se necessário, todos implementando `NotificationPort`.

### Padrão estabelecido para novos canais

1. Adicionar valor ao enum `NotificationChannel`
2. Criar `XyzProperties` com `@ConfigurationProperties`
3. Criar `XyzNotificationAdapter implements NotificationPort`
4. `channel()` retorna o novo canal
5. `send()` chama a API do provedor
6. Teste com MockWebServer

O `NotifyUseCase` e o `TranscriptionCompletedConsumer` **não mudam**.

## Projeto concluído — v3.0.0

Com a v9.3.0, o roadmap completo do dio-speech-ai está entregue:

```
Áudio entra (HTTP ou fila)
    → cache SHA-256 (~15ms hit)
    → Whisper via Speaches (CircuitBreaker + Retry)
    → Redis TTL 24h
    → RabbitMQ: TranscriptionCompletedEvent
    → E-mail / SMS / WhatsApp
```

Observabilidade: Prometheus + Grafana + Zipkin + logs JSON + MDC  
CI/CD: GitHub Actions + SonarCloud + Jacoco 70% + Docker Hub  
Arquitetura: Hexagonal (Ports & Adapters) em todos os domínios
