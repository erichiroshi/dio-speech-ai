## Decisões e trade-offs

### Por que bean `RedisTemplate` separado para resumos?

O projeto já tem `RedisTemplate<String, TranscriptionResult>` em `shared/config/RedisConfig.java`.
Criar um segundo bean `RedisTemplate<String, SummaryResult>` com nome diferente evita:

1. Ambiguidade de injeção (Spring não saberia qual `RedisTemplate` injetar)
2. Conflito de tipo na deserialização (Jackson não saberia se o valor é `TranscriptionResult` ou `SummaryResult`)

O bean é nomeado `summaryRedisTemplate` via parâmetro do `@Bean` para injeção explícita:
```java
private final RedisTemplate<String, SummaryResult> summaryRedisTemplate;
```

### Por que chave `summary:{hash}` e não `analysis:{hash}`?

`summary` é mais descritivo do que `analysis` — representa o conteúdo armazenado
(um resumo), não a operação realizada. Consistente com `transcription:{hash}`.

### Por que TTL de 72h para resumos vs 24h para transcrições?

Resumos são mais custosos de gerar (chamada ao LLM, 5-30s) do que transcrições
(chamada ao Whisper, ~800ms). Um TTL mais longo reduz o número de chamadas ao Ollama.

**Trade-off:** resumos ficam no Redis mais tempo, consumindo mais memória.
Para volumes baixos é irrelevante. Para volumes altos, ajustar via `CACHE_SUMMARY_TTL_HOURS`.

### Por que `audioHash` no `TranscriptionResult` e não calculado no controller?

Opções consideradas:

1. **Controller recalcula o SHA-256** — viola single responsibility: o controller
   não deveria conhecer a estratégia de hash do domínio.

2. **Use case retorna o hash no result** ← escolha feita. O use case já calcula
   o hash internamente para o cache. Incluir no result é custo zero e elimina
   duplicação de lógica.

3. **Endpoint separado `GET /api/transcriptions/{hash}`** — exigiria armazenar
   o texto transcrito associado ao hash de forma indexada. Mais complexo sem
   benefício adicional para o caso de uso atual.

### Breaking change na resposta de transcrição

Adicionar `audioHash` ao `TranscriptionResponse` é uma adição retrocompatível
(campo novo, não removido). Clientes existentes que ignoram campos desconhecidos
continuam funcionando. O campo é `@JsonInclude(NON_NULL)` — não aparece quando null.

## Fase 10 — Resumo completo

| Versão | O que foi entregue |
|---|---|

| v10.2.0 | `RedisSummaryStoreAdapter`, `RedisAnalysisConfig`, `audioHash` na resposta de transcrição, teste do adapter Redis |

### Fluxo completo de uso

```
1. POST /api/transcriptions
   → { text, fileSizeBytes, audioHash: "a1b2c3..." }

2. POST /api/transcriptions/a1b2c3.../analysis
   → SummarizeTranscriptionUseCase
   → summaryStore.get("a1b2c3...") → miss (primeira vez)
   → transcriptionCachePort.get("a1b2c3...") → texto
   → languageModelPort.generate(prompt) → Ollama (~5-30s)
   → summaryStore.put("a1b2c3...", result)
   → { audioHash, summary, model: "llama3.2:3b" }

3. POST /api/transcriptions/a1b2c3.../analysis (segunda vez)
   → summaryStore.get("a1b2c3...") → hit
   → { audioHash, summary, model, cached: true }  (~15ms)
```

### O que este projeto demonstra agora

- API REST completa com dois canais de entrada (HTTP + RabbitMQ)
- Cache distribuído SHA-256 (Redis)
- Resiliência (CircuitBreaker + Retry)
- Observabilidade (Prometheus + Grafana + Zipkin + Logs JSON)
- Mensageria assíncrona (RabbitMQ)
- Notificações multicanal (e-mail + SMS + WhatsApp)
- Arquitetura Hexagonal (Ports & Adapters) em todos os domínios
- **IA local com Spring AI + Ollama** — sem API key, sem custo, offline
- CI/CD completo com cobertura de testes ≥ 70%
