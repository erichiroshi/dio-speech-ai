# v2.4.0 — Cache de transcrições por hash SHA-256

Implementação da lógica de cache: calcular o SHA-256 do conteúdo binário do arquivo de áudio, usar esse hash como chave no Redis, e retornar a transcrição cacheada quando disponível.

## Por que SHA-256 do conteúdo, não do nome?

O nome do arquivo é metadado — não descreve o conteúdo. O mesmo arquivo de áudio pode chegar como `audio.wav`, `gravacao_final.wav`, `teste_v3.wav` ou qualquer outro nome. O Whisper produziria a mesma transcrição para todos.

SHA-256 é uma função hash criptográfica: dado um input, sempre produz o mesmo output de 256 bits (64 chars hexadecimais). Dois arquivos com o mesmo conteúdo binário **sempre** produzem o mesmo hash. Dois arquivos diferentes com conteúdo diferente produzem hashes diferentes (colisão é computacionalmente inviável).

```java
MessageDigest digest = MessageDigest.getInstance("SHA-256");
byte[] hash = digest.digest(fileBytes);
String key = "transcription:" + HexFormat.of().formatHex(hash);
// → "transcription:3a14c5038f8ff8fcdd2d0e7af62f1e3bb5e2b4a9..."
```

SHA-256 está disponível em toda JVM (garantido pela spec), portanto `NoSuchAlgorithmException` nunca ocorre na prática — mas é tratada com `IllegalStateException` por completude.

## O padrão cache-aside

O cache-aside (também chamado lazy loading) é o padrão mais comum para cache de leitura:

```
1. Chega a requisição
2. Calcula a chave (SHA-256)
3. Busca no Redis
   ├── HIT  → retorna imediatamente (cached=true)
   └── MISS → processa (chama Whisper)
              → armazena no Redis com TTL
              → retorna resultado
```

A aplicação é responsável por gerenciar o cache explicitamente — o Redis não sabe nada sobre a lógica de negócio. Isso dá controle total sobre quando cachear, com qual TTL, e como invalidar.

## Tolerância a falhas do Redis

Uma decisão importante: se o Redis estiver indisponível, a requisição **não falha** — ela continua e chama o Whisper normalmente.

```java
public TranscriptionResponse get(byte[] fileBytes) {
    try {
        return redisTemplate.opsForValue().get(buildKey(fileBytes));
    } catch (Exception ex) {
        log.warn("Falha ao ler cache Redis — continuando sem cache");
        return null;  // trata como miss
    }
}
```

Cache é otimização, não dependência crítica. A disponibilidade da API não deve depender da disponibilidade do cache. Se o Redis cair às 3h da manhã, as transcrições continuam funcionando — apenas mais lentas.

## O campo cached na resposta

`TranscriptionResponse` ganhou o campo `cached` com `@JsonInclude(NON_NULL)`:

```json
// Cache miss — campo ausente
{ "text": "...", "fileSizeBytes": 461842 }

// Cache hit — campo presente
{ "text": "...", "fileSizeBytes": 461842, "cached": true }
```

A anotação `NON_NULL` garante que `"cached": null` nunca apareça na resposta. O campo só existe quando `true` — quando ausente, a transcrição foi processada agora. Isso mantém a resposta limpa e é retrocompatível (clientes antigos não veem o campo).

O método `asCached()` no record retorna uma cópia imutável marcada como cache hit:
```java
public TranscriptionResponse asCached() {
    return new TranscriptionResponse(text, fileSizeBytes, true);
}
```

## TTL configurável

O TTL padrão é 24 horas, configurável via variável de ambiente:

```yaml
cache:
  transcription:
    ttl-hours: ${CACHE_TTL_HOURS:24}
```

No perfil dev, o TTL é 1 hora — facilita testes sem precisar limpar o Redis manualmente. Em prod, 24 horas é razoável para o caso de uso: áudios de treinamento, batches de CI/CD, chamadas repetidas do mesmo cliente.

## Impacto nos tempos de resposta

| Cenário | Tempo |
|---|---|
| Primeira requisição (container frio) | 4–5 segundos |
| Requisições sem cache (container quente) | 800ms – 1s |
| Cache hit em dev | 15–20ms |
| Cache hit em prod | ~50ms |

A diferença de 40x a 60x na latência. Para o usuário final: a primeira transcrição demora o esperado, todas as seguintes com o mesmo áudio são praticamente instantâneas.

## Trade-offs

| Decisão | Alternativa | Por que esta |
|---|---|---|
| SHA-256 do conteúdo | nome do arquivo como chave | Nome é metadado, conteúdo é identidade |
| Cache-aside (manual) | `@Cacheable` do Spring | Controle explícito sobre TTL por tipo, lógica de fallback, e campo `cached` na resposta |
| Tolerância a falhas (miss forçado) | Propagar exceção do Redis | Cache é otimização; disponibilidade da API não depende do cache |
| `@JsonInclude(NON_NULL)` | campo `cached: false` em miss | Resposta mais limpa; retrocompatível com clientes que não conhecem o campo |
| TTL fixo por configuração | TTL por tipo de arquivo | Simplicidade; pode ser evoluído para TTL dinâmico se necessário |
