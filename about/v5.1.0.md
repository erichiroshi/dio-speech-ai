## Jacoco — cobertura de testes

### Por que 70%?

O projeto tem um `TranscriptionIntegrationTest` robusto com Testcontainers que
cobre o fluxo completo. Mas classes como `GlobalExceptionHandler` e
`TranscriptionMetrics` precisam de testes unitários específicos que ainda não
existem. Começar com 80% travaria o CI imediatamente.

A estratégia é subir o threshold gradualmente conforme os testes das fases
seguintes aumentam a cobertura. 70% bloqueia regressões sem criar atrito
desnecessário agora.

### Como funciona no build.gradle

```groovy
test.finalizedBy jacocoTestReport
check.dependsOn jacocoTestCoverageVerification
```

`test.finalizedBy` garante que o relatório é gerado sempre após os testes,
mesmo em falha. `check.dependsOn` garante que o threshold é verificado antes
de qualquer `build` — o Gradle não vai empacotar o JAR se a cobertura estiver
abaixo do mínimo.

### Exclusões do threshold

```
**/config/**         → beans de configuração Spring — não têm lógica testável
**/dto/**            → records sem comportamento
**/exception/*Exception*  → classes de exceção simples (só construtores)
**/*Application*     → entry point do Spring Boot
**/documentation/**  → interfaces de documentação Swagger
```

Excluir essas classes do threshold não significa que não serão testadas —
o Jacoco ainda as conta no relatório. Significa que elas não penalizam o
threshold quando não têm cobertura.

### Relatórios gerados

```
build/reports/jacoco/test/index.html  → leitura local (abrir no browser)
build/reports/jacoco/test/jacocoTestReport.xml → consumido pelo SonarCloud e Codecov
```

## SonarCloud

### Configuração via build.gradle

Em vez de um arquivo `sonar.properties` separado, a configuração fica inline
no `build.gradle` dentro do bloco `sonar{}`. Isso mantém tudo em um lugar só
e aparece no `git diff` quando algo muda.

### Propriedades principais

| Propriedade | Valor |
|---|---|
| `sonar.projectKey` | `erichiroshi_dio-speech-ai` |
| `sonar.organization` | `erichiroshi` |
| `sonar.coverage.jacoco.xmlReportPaths` | `build/reports/jacoco/test/jacocoTestReport.xml` |

O `SONAR_TOKEN` nunca entra no código — vem da variável de ambiente no CI
(`secrets.SONAR_TOKEN`) ou da variável de ambiente local.

### Trade-off: SonarCloud vs SonarQube local

SonarQube local exige um servidor rodando. SonarCloud é gratuito para projetos
públicos, integra com GitHub Actions, adiciona comentários automáticos em PRs
e expõe um badge no README. Para um portfólio, o badge verde é um sinal visível
de qualidade que recrutadores e tech leads reconhecem.

## Remoção do JWT

### Por que remover agora?

A implementação JWT aceitava qualquer username sem verificar credenciais. Manter
uma falsa sensação de segurança é tecnicamente pior do que não ter segurança —
confunde quem lê o código e dá uma impressão errada da postura de segurança do
sistema.

Segurança real (RBAC, refresh token, integração com IdP) volta em fase futura
com implementação correta.

### Impacto no comportamento

- `POST /auth/token` removido
- `POST /api/transcriptions` agora é público (sem autenticação)
- Testes de 401/403 removidos do `TranscriptionIntegrationTest`
- `GlobalExceptionHandler` sem handler `JwtValidationException`

### Novos testes adicionados

Com a remoção do JWT, dois novos testes foram adicionados ao
`TranscriptionIntegrationTest` que antes eram mascarados pela autenticação:

- `shouldReturn400WhenFileMissing()` — ausência do campo `file`
- `shouldReturn400WhenInvalidContentType()` — Content-Type inválido (antes precisava de token)

## Dockerfile multistage

### Por que multistage?

O Dockerfile anterior copiava o JAR pré-compilado (`build/libs/*.jar`),
assumindo que o `./gradlew bootJar` tinha rodado antes do `docker build`.
Isso cria um acoplamento entre o pipeline local e o Docker.

O multistage compila dentro do próprio Docker:

```
Stage builder → JDK 25 completo → compila e empacota o JAR
Stage runtime → JRE 25 apenas → copia só o JAR do stage anterior
```

A imagem final não tem `javac`, `gradle`, código-fonte nem arquivos de build —
só o JRE e o JAR. Resultado: imagem menor e sem ferramentas desnecessárias.

### Cache BuildKit com --mount=type=cache

```dockerfile
RUN --mount=type=cache,target=/root/.gradle \
    ./gradlew dependencies --no-daemon --quiet
```

O `--mount=type=cache` monta um cache persistente no daemon Docker para o
diretório `.gradle`. As dependências baixadas em um build são reutilizadas
no próximo sem precisar do cache de camadas do Docker. Isso é especialmente
útil no CI com `type=gha` no `docker.yml`.

### Trade-off

O stage de build dentro do Docker significa que o JAR não precisa existir
antes do `docker build`. Mas o build demora mais do que simplesmente copiar
um JAR pronto. No CI, o `docker.yml` usa `cache-from/to: type=gha` para
reutilizar camadas entre execuções, compensando o overhead.

## GlobalExceptionHandler — idioma padronizado

Mensagens padronizadas em português em todos os handlers. Antes havia uma
mistura de inglês (`"Validation Error"`, `"You do not have permission"`) com
português. A consistência é mais importante do que a escolha do idioma.

```java
// Antes
"Validation Error"   → "Erro de Validação"
"Access Denied"      → "Acesso Negado"

// Padronizado nesta versão
"Requisição Inválida"
"Serviço Indisponível"
"Método Não Permitido"
"Não Encontrado"
"Erro Interno"
```
