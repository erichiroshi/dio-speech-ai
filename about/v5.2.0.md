# v5.2.0 — ci.yml + docker.yml (GitHub Actions)

## O que foi feito

Criação dos dois workflows principais do GitHub Actions: `ci.yml` para testes
e qualidade, e `docker.yml` para build e publicação da imagem.

| Arquivo | Descrição |
|---|---|
| `.github/workflows/ci.yml` | Testes + Jacoco + SonarCloud + Codecov |

## ci.yml

### Disparo

```yaml
on:
  push:
    branches: [ "**" ]    # qualquer branch
  pull_request:
    branches: [ "main" ]  # PR para main
```

Todo push de qualquer branch recebe feedback de testes. PRs para main
rodam um check adicional antes do merge.

### Por que `fetch-depth: 0`?

O SonarCloud analisa apenas as linhas alteradas em relação ao branch base
(`pull_request` events) ou ao commit anterior (`push` events). Para isso
ele precisa do histórico completo do repositório — `fetch-depth: 0` garante
que o clone não é superficial (shallow clone).

Com um shallow clone, o SonarCloud não consegue calcular o diff correto
e pode deixar de reportar issues ou reportar falsos positivos.

### Cache em duas camadas

**Cache Gradle** via `actions/setup-java`:
```yaml
- uses: actions/setup-java@v4
  with:
    cache: gradle
```
O `setup-java` gerencia o cache do `~/.gradle` automaticamente usando o
hash do `build.gradle` como chave. Quando as dependências não mudam, o
step de download é pulado.

**Cache SonarCloud** via `actions/cache`:
```yaml
- uses: actions/cache@v4
  with:
    path: ~/.sonar/cache
    key: ${{ runner.os }}-sonar
```
O SonarCloud baixa regras e plugins na primeira execução. O cache evita
esse download nas execuções seguintes, acelerando o step `./gradlew sonar`.

### Por que `if: always()` no upload do Jacoco?

```yaml
- uses: actions/upload-artifact@v4
  if: always()
```

O relatório HTML do Jacoco é mais útil quando os testes falham do que
quando passam. Se o CI falhou porque a cobertura caiu abaixo de 70%, o
relatório mostra exatamente quais linhas não estão cobertas. `always()`
garante que o artifact é salvo mesmo quando o step anterior falhou.

## docker.yml

### Por que dois workflows separados?

O `ci.yml` roda em ~3 minutos (só JDK e Gradle).
O `docker.yml` roda em ~8-15 minutos (build Docker com multistage).

Separar garante que o feedback de testes chega rápido sem esperar o
build Docker inteiro. Um dev fazendo push em uma branch de feature
quer saber se os testes passam, não se a imagem Docker buildou.

### Tags geradas pelo metadata-action

```yaml
tags: |
  type=sha,format=short          # sha-abc1234 — rastreabilidade por commit
  type=ref,event=branch          # feature-x, main, develop
  type=ref,event=pr              # pr-42 (sem push)
  type=raw,value=latest,enable=${{ github.ref == 'refs/heads/main' }}
```

Na prática:
- Push na `main` → `latest` + `main` + `sha-abc1234`
- Push na `feature/x` → `feature-x` + `sha-abc1234`
- PR para `main` → `pr-42` (imagem buildada mas não publicada)

### Cache de camadas com type=gha

```yaml
cache-from: type=gha
cache-to:   type=gha,mode=max
```

`type=gha` usa o GitHub Actions Cache como backend de camadas Docker.
É significativamente mais rápido que baixar e rebuildar camadas em cada
execução. `mode=max` salva todas as camadas intermediárias, não só a final.

O cache é invalidado automaticamente quando a camada muda (ex: quando
`build.gradle` muda, a camada de dependências é reconstruída).

### Por que não publicar em PRs?

```yaml
push: ${{ github.event_name != 'pull_request' }}
load: ${{ github.event_name == 'pull_request' }}
```

Em PRs, a imagem é buildada (`load: true` carrega no daemon local) mas não
publicada no Docker Hub. Isso permite que o Trivy faça o scan mesmo em PRs,
sem poluir o registry com imagens de branches temporárias.

### Trivy com exit-code 0

```yaml
exit-code: '0'
severity: CRITICAL,HIGH
```

Vulnerabilidades CRITICAL e HIGH são reportadas no log mas não bloqueiam o CI.
Em produção real, `exit-code: '1'` bloquearia o build. Para um projeto de
portfólio, vulnerabilidades em dependências transitivas do Spring Boot
gerariam ruído sem valor — o foco é na visibilidade, não no bloqueio.

## Secrets necessários

Adicionar em **Settings → Secrets and variables → Actions** do repositório:

| Secret | Como obter |
|---|---|
| `DOCKERHUB_USERNAME` | `erichiroshi` |
| `DOCKERHUB_TOKEN` | Docker Hub → Account Settings → Security → New Access Token |
| `SONAR_TOKEN` | sonarcloud.io → My Account → Security → Generate Tokens |
| `CODECOV_TOKEN`` | codecov.io → Settings → Repository Upload Token |

### Por que usar token Docker Hub e não senha?

Tokens Docker Hub têm escopo limitado (read/write/delete) e podem ser
revogados individualmente sem trocar a senha da conta. Se um token vazar,
basta revogá-lo. Com a senha, seria necessário trocar a senha de toda a conta.
