## O que foi feito

---

## O problema que o CircuitBreaker resolve

Sem proteção, uma dependência externa lenta ou offline causa falha em cascata:

1. Speaches fica fora do ar
2. Cada chamada ao Whisper espera 30s pelo timeout
3. Threads do Tomcat ficam bloqueadas esperando
4. Pool de threads esgota
5. Novas requisições (inclusive para endpoints saudáveis) passam a falhar

O CircuitBreaker interrompe esse ciclo: após detectar um número de falhas acima do threshold, ele **para de fazer chamadas** e responde imediatamente com o fallback.

---

## Os três estados

```
CLOSED ──(≥50% falhas em 10 calls)──► OPEN
  ↑                                      │
  └──(3 calls ok em HALF_OPEN)──◄── (30s espera)
                                    HALF_OPEN
```

- **CLOSED**: operação normal. Todas as chamadas passam para o Whisper.
- **OPEN**: circuito aberto. Fallback imediato (HTTP 503) sem tocar o Whisper. Dura `waitDurationInOpenState` (30s).
- **HALF_OPEN**: sondagem. Permite `permittedNumberOfCallsInHalfOpenState` (3) chamadas de teste. Se passarem: fecha o circuito. Se qualquer uma falhar: reabre.

---

## Configuração prod vs dev

```yaml
# Prod
resilience4j.circuitbreaker.instances.whisper:
  slidingWindowSize: 10        # analisa as últimas 10 chamadas
  minimumNumberOfCalls: 5      # precisa de no mínimo 5 antes de calcular
  failureRateThreshold: 50     # abre se ≥50% falharem
  waitDurationInOpenState: 30s

# Dev — janela menor para testar o comportamento rapidamente
resilience4j.circuitbreaker.instances.whisper:
  slidingWindowSize: 5
  minimumNumberOfCalls: 3
  waitDurationInOpenState: 10s
```

## Por que spring-boot4 e não spring-boot3?

O módulo `resilience4j-spring-boot3` funciona com Spring Boot 3.x. Para Spring Boot 4.x, foi lançado o `resilience4j-spring-boot4`. Usar o módulo errado resulta em autoconfigure que não é acionado — as anotações `@CircuitBreaker` e `@Retry` são ignoradas silenciosamente.

## Por que AOP é necessário?

`@CircuitBreaker` é uma anotação de aspecto — ela funciona via proxy Spring. Para que o proxy seja criado, `spring-boot-starter-aop` precisa estar no classpath. Sem ele, a anotação é um comentário decorativo.

## Por que management.health.circuitbreakers.enabled: true?

Por padrão, o Resilience4j registra o estado dos circuit breakers no Actuator Health, mas o indicador não é exposto a menos que seja habilitado explicitamente. Sem essa configuração, `/actuator/health` não mostra o estado do CB.

---

## Trade-offs

| Decisão | Alternativa | Por que esta |
|---|---|---|
| Fallback lança exceção (503) | Fallback retorna resposta parcial | Para transcrição, não há dado parcial útil — é melhor falhar explicitamente |
| Threshold 50% | Threshold mais alto (80%) | 50% significa que metade das chamadas estão falhando — situação que já justifica abrir o circuito |
| slidingWindow por contagem | slidingWindow por tempo | Por contagem é mais previsível em carga variável |

# v3.2.0 — Retry com backoff exponencial

## O que foi feito

Adição de `@Retry` em cima do `@CircuitBreaker` no `SpeechToTextClient`. A ordem importa: Retry é executado primeiro, CircuitBreaker por baixo.

### Arquivos alterados

| Arquivo | Tipo | O que mudou |
|---|---|---|
| `build.gradle` | modificado | version `3.2.0` |
| `application.yml` | modificado | + `resilience4j.retry` |
| `SpeechToTextClient.java` | modificado | + `@Retry` acima do `@CircuitBreaker` |

---

## A cadeia de decoração

```
Retry
  └── CircuitBreaker
        └── SpeechToTextClient.transcribe()
```

Quando a chamada falha com `TranscriptionException`:

1. Retry intercepta e tenta novamente (até 3 vezes, com backoff)
2. Se após 3 tentativas ainda falhar, a exceção chega ao CircuitBreaker
3. O CircuitBreaker registra a falha na janela deslizante
4. Se a taxa de falha atingir o threshold, o circuito abre

---

## Backoff exponencial

```yaml
retry.instances.whisper:
  maxAttempts: 3
  waitDuration: 500ms
  enableExponentialBackoff: true
  exponentialBackoffMultiplier: 2   # 500ms → 1s → 2s
  exponentialMaxWaitDuration: 4s
```

O backoff exponencial evita o problema de "thundering herd": se o Whisper está sobrecarregado, múltiplas requisições tentando novamente ao mesmo tempo ao mesmo instante pioram a situação. Com backoff crescente, as retentativas são espaçadas.

O `exponentialMaxWaitDuration: 4s` garante um teto: sem limite, o backoff poderia crescer indefinidamente em caso de múltiplas falhas encadeadas.

---

## Retry NÃO ocorre para

```yaml
ignoreExceptions:
  - ServiceUnavailableException   # CB aberto — já sabemos que vai falhar
  - IllegalArgumentException      # erro de validação do cliente — retry não ajuda
```

Fazer retry quando o circuito está aberto seria inútil — o fallback dispara imediatamente de qualquer forma. E fazer retry em erros de validação (arquivo inválido, por exemplo) seria retransmitir algo que vai falhar sempre.

---

## Trade-offs

| Decisão | Alternativa | Por que esta |
|---|---|---|
| Backoff exponencial | Backoff fixo | Evita thundering herd; dá mais tempo ao serviço para se recuperar |
| maxAttempts=3 | maxAttempts=5 | 3 tentativas × 30s timeout cada = até 90s de espera máxima; mais do que isso prejudica o usuário |
| Retry acima do CB | CB acima do Retry | Com CB acima: uma falha no Retry conta uma vez para o CB. Com Retry acima: cada tentativa conta — o CB acumula falhas mais rapidamente |

## Integração automática Resilience4j → Micrometer

O Resilience4j detecta o `MeterRegistry` no contexto Spring e registra métricas automaticamente para cada instância configurada. Não é necessário nenhum código de instrumentação.

As métricas disponíveis:

| Métrica | Descrição |
|---|---|
| `resilience4j_circuitbreaker_state` | Estado: 0=CLOSED, 1=OPEN, 2=HALF_OPEN |
| `resilience4j_circuitbreaker_calls_seconds_count` | Chamadas por tipo: successful, failed, not_permitted, slow |
| `resilience4j_retry_calls_total` | Chamadas por resultado: successful_with_retry, failed_with_retry |

## Por que o painel de estado do CB importa

Sem o painel, você descobre que o Whisper caiu quando o cliente liga reclamando. Com o painel `resilience4j_circuitbreaker_state`, você vê o estado em tempo real. Além disso, ao ver `not_permitted` subindo (chamadas bloqueadas pelo CB aberto), você sabe que o CircuitBreaker está funcionando — o fallback está sendo acionado, não o Whisper.

## Correção das queries com sum()

Durante a v2.6.0, algumas queries de divisão entre séries com labels diferentes geravam `No data` no Grafana. A correção foi envolver cada `rate()` com `sum()` antes de dividir — isso agrega os vetores e permite a divisão.

Exemplo corrigido:
```promql
# Antes (quebrado)
rate(transcription_cache_total{result="hit"}[5m])
  / rate(transcription_cache_total{result="miss"}[5m])

# Depois (correto)
sum(rate(transcription_cache_total{result="hit"}[5m]))
  / sum(rate(transcription_cache_total{result="miss"}[5m]))
```
