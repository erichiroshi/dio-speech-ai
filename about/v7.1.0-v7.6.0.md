# Fase 7 — Arquitetura Hexagonal (v7.1.0 a v7.6.0)

## Por que refatorar?

O projeto chegou na v5.3.0 com uma arquitetura por camadas funcional. Mas havia
um acoplamento central: `TranscriptionService` conhecia `SpeechToTextClient` (Whisper),
`CacheService` (Redis) e `TranscriptionMetrics` ao mesmo tempo. Para trocar o
Whisper por outro provedor de IA, seria preciso mexer no service de negócio.

A arquitetura hexagonal resolve isso invertendo as dependências: o domínio define
interfaces (ports), a infraestrutura as implementa (adapters). O domínio nunca
importa frameworks, nunca conhece Redis, Whisper, RabbitMQ ou HTTP.

---

## v7.1.0 — Entidade + ports de saída

### Por que criar entidade separada de DTO?

`TranscriptionResponse` era um DTO HTTP com `@Schema` do Swagger e
`@JsonInclude`. Não representa um conceito de domínio — representa uma resposta
de API. A entidade `Transcription` é o conceito de domínio: tem identidade
(UUID), tem `audioHash`, tem `createdAt`. Zero import de framework.

### Por que `NoOpTranscriptionEventAdapter`?

O `TranscribeAudioUseCase` (v7.3.0) chama `eventPort.publish()` desde o início.
Para que o Spring consiga inicializar o contexto sem RabbitMQ, precisamos de
uma implementação concreta do `TranscriptionEventPort`. O no-op faz isso:
apenas loga, não publica. Na Fase 8, é substituído pelo adapter RabbitMQ.

**Trade-off:** o no-op precisa estar excluído do threshold do Jacoco (adicionado
em `coverageExclusions`) — não tem lógica testável além de um log.

## v7.2.0 — Port de entrada + command/result

### Por que `TranscribeCommand` e não `MultipartFile`?

Se o caso de uso recebesse `MultipartFile`, ele dependeria do servlet container
do Spring. O teste unitário precisaria de um mock de `MultipartFile`. Com
`TranscribeCommand(byte[], String, long)`, o teste cria o objeto diretamente
sem nenhum mock de framework.

### Por que `TranscriptionResult` e não `TranscriptionResponse`?

`TranscriptionResponse` tem `@Schema`, `@JsonInclude`, `Boolean cached` — é uma
representação HTTP. `TranscriptionResult` é um objeto de transferência do caso
de uso: `text`, `fileSizeBytes`, `boolean cached`. O adapter HTTP converte
`TranscriptionResult` para `TranscriptionResponse` na fronteira.

---

## v7.3.0 — TranscribeAudioUseCase

### Por que o SHA-256 está no use case e não no adapter de cache?

O hash é calculado no use case porque é uma decisão de negócio: dois arquivos
com conteúdo idêntico são a mesma coisa para fins de cache. O adapter de cache
recebe o hash pronto — não precisa saber como ele foi calculado.

Se amanhã a estratégia de cache mudar para MD5 ou para um hash de fingerprint
de áudio, a mudança fica no use case, não no adapter.

### Teste unitário puro — o maior ganho da Fase 7

```java
@ExtendWith(MockitoExtension.class)
class TranscribeAudioUseCaseTest {
    @Mock SpeechToTextPort speechPort;
    @Mock TranscriptionCachePort cachePort;
    @Mock TranscriptionEventPort eventPort;
    @Mock TranscriptionMetrics metrics;
    @InjectMocks TranscribeAudioUseCase useCase;
}
```

- Zero Spring context (sem `@SpringBootTest`)
- Zero Docker (sem Testcontainers)
- Zero Redis (sem `RedisContainer`)
- Zero Whisper (sem `MockWebServer`)
- Executa em ~20ms

Antes, para testar o fluxo de cache era necessário o `TranscriptionIntegrationTest`
com Redis real — ~10 segundos de startup. Agora o mesmo cenário testa em ~20ms.

## v7.4.0 — Adapters de infraestrutura

### WhisperAdapter vs SpeechToTextClient

| | SpeechToTextClient (antes) | WhisperAdapter (depois) |
|---|---|---|
| Interface | Nenhuma — classe concreta | Implementa `SpeechToTextPort` |
| Parâmetro | `MultipartFile` | `byte[]` — desacoplado do HTTP |
| DTO interno | `WhisperResponse` (pacote público) | Record privado interno |
| Localização | `transcription/service/` | `transcription/infrastructure/speechtotext/whisper/` |

### RedisTranscriptionCacheAdapter vs CacheService

A mudança mais importante: `Optional<TranscriptionResult>` em vez de nullable.
O `Optional` força o chamador (o use case) a tratar explicitamente o caso de miss
sem depender de verificação de `null`. É mais seguro e mais expressivo.

### Por que `RedisConfig` foi movido para `shared/config/`?

`RedisConfig` é infraestrutura transversal — configura um bean usado pelo domínio
de transcrição via adapter. Não pertence ao pacote de transcrição nem ao antigo
`config/` flat. `shared/config/` é o lugar semântico correto para configurações
de infraestrutura que cruzam domínios.

O tipo do `RedisTemplate` foi atualizado de `TranscriptionResponse` (DTO HTTP)
para `TranscriptionResult` (objeto do domínio application) — alinhado com o
que o `RedisTranscriptionCacheAdapter` precisa.

## v7.5.0 — Controller refatorado + reorganização de pacotes

### TranscriptionController antes e depois

```java
// Antes
private final TranscriptionService service;
return ResponseEntity.ok(service.transcribe(file));

// Depois
private final TranscribeAudioPort transcribePort;
var command = new TranscribeCommand(file.getBytes(), file.getOriginalFilename(), file.getSize());
var result  = transcribePort.transcribe(command);
return ResponseEntity.ok(toResponse(result));
```

O controller passou a ter uma responsabilidade única: converter MultipartFile
para TranscribeCommand e TranscriptionResult para TranscriptionResponse.
Não conhece Redis, Whisper, SHA-256 nem eventos.

### Pacote shared/

Criado para conter o que é transversal a todos os domínios:
- `shared/config/` — beans de infraestrutura que qualquer domínio pode usar
- `shared/exception/` — `GlobalExceptionHandler` trata exceções de qualquer domínio

**Trade-off:** em projetos maiores, `GlobalExceptionHandler` poderia estar
em cada domínio separadamente. Para este projeto com um domínio, `shared/exception/`
é a organização mais limpa.

## v7.6.0 — Testes e encerramento

### Por que a tag v2.0.0?

`v2.0.0` é um marco semântico, não uma versão de código. Marca a conclusão de
uma mudança arquitetural significativa — o domínio passou a ser completamente
desacoplado da infraestrutura.

Versões de código seguem MAJOR=fase, MINOR=item (`v7.6.0`).
Marcos arquiteturais usam SemVer livre: `v2.0.0` = hexagonal completo,
`v3.0.0` = mensageria, `v4.0.0` = notificações.

### Cobertura de testes após Fase 7

Dois testes complementares:
- `TranscribeAudioUseCaseTest` — 5 cenários de negócio, ~20ms, zero infra
- `TranscriptionIntegrationTest` — 5 cenários E2E, ~15s, Redis + MockWebServer

O `TranscribeAudioUseCaseTest` cobre a lógica de negócio com velocidade.
O `TranscriptionIntegrationTest` verifica que os adapters reais funcionam juntos.

## Diferença arquitetural: antes vs depois

### Antes (v5.3.0) — por camadas

```
TranscriptionController
    → TranscriptionService     (conhece Redis, Whisper, métricas)
        → SpeechToTextClient   (WebClient + Retry + CB)
        → CacheService         (Redis + SHA-256)
        → TranscriptionMetrics
```

### Depois (v7.6.0) — hexagonal

```
TranscriptionController (adapter HTTP)
    → TranscribeAudioPort (interface)
        → TranscribeAudioUseCase (lógica pura)
            → SpeechToTextPort    → WhisperAdapter
            → TranscriptionCachePort → RedisTranscriptionCacheAdapter
            → TranscriptionEventPort → NoOpTranscriptionEventAdapter (Fase 8: Rabbit)
            → TranscriptionMetrics
```

O use case não sabe que existe WebClient, Redis ou RabbitMQ.
